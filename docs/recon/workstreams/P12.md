## Decisions

### D12-001 · 2026-11-27 · Compute lanes are enforced by the code that starts the workers

Section 5 was a convention (a lock wrapped by hand). `core/lanes.py` now makes it code: `plan(lane, requested, leased,
memory)` is the pure rule of the table (authoritative 3 workers, 4 for a resumed run; development-heavy 1 worker, niceness
19 and a 1.5 GiB cap while P7's lease is live, else up to 2 and no more than memory fits next to a quarter-of-the-machine
reserve; light 1 processor, niceness 19 while the lease is live), and `enter(lane, root, ...)` applies it to the process
(inherited by every worker) and publishes it for `workers.Pool`. The heavy lane takes `ws/locks/dev-heavy.lock` with
`flock(2)`, the same lock `flock(1)` takes, so a run wrapped by hand and one that enters the lane exclude each other;
while it waits it says who holds it (`dev-heavy.lock.holder`). The pool reads the plan: its worker limit is lowered,
never raised; a worker past the lane's cap is retired after its task; a lease that appears during a heavy run lowers its
limit to one at the pool's next step. A lane never ends a task and never refuses a run (at least one worker): ending a
task would turn a function's record into `INFRA`, which changes what a run reports, and C8 says lanes decide only when and
where. So the 1.5 GiB cap is enforced between tasks; a single task's peak is bounded only by the budgets (D-047).

`campaign` and `prewarm` take `--lane auto|authoritative|heavy` (default auto: authoritative when every path they write
is under `phase7/`, development-heavy otherwise); naming the authoritative lane for a private store is refused. That is a
small separate commit on `cli/*`, which P7 owns, for P7's review at the merge. Before C0, D-065's `workload.py` is not in
this branch, so `lanes.lease` reads the same lease format itself; at C0 it becomes a call of `workload.holder`.

Tests: `tests/unit/test_lanes.py` (the table, the lease of a live and an ended process, the lock across processes and
against `fcntl.flock` as the command line takes it, a pool that follows the lane and drops to one worker when a lease
appears with identical answers, the cap retiring workers between tasks).

### D12-002 · 2026-11-27 · Where an authoritative cycle's time goes (measured before optimising)

From P7's D-060 records (`phase7-final-d060.jsonl`, read-only copy; per-function `ms` is the pool's task time, worker
time not wall time) and from profiling three functions on a private cold store in the light lane:

| Part (D-060 campaign, 2,249 functions) | Worker time | Share |
|---|---|---|
| reach, all functions (mean 391 ms when solve does not run, 1,304 ms when it does) | 1,611 s | 28% |
| solve, search (generator, candidate compiles, comparator) for 809 functions | 2,621 s | 45% |
| solve, around the search (context, class facts: 2 compiles each) for 809 functions, median 1.84 s each | 1,561 s | 27% |
| total | 5,843 s (1.62 h) | |

* wine and `cl.exe`: a process start costs 0.40 to 0.47 s wall (2.4 s for the first, which starts `wineserver`); a small
  unit header adds little (0.43 to 0.52 s); four units in one `cl` invocation take 0.52 s against 4 x 0.45 s. The objects
  of two compiles of the same text differ in the COFF time stamp only; a different `/Fo` path also changes the
  `S_OBJNAME` record of `.debug$S`. So "byte-identical" (C5) can only mean: equal but for the time stamp, given the same
  output path.
* A solved function with 5 candidate compiles (profiled, cold store): 25 s, of which 7 compiler processes 12.8 s (5
  candidates 8.8 s, class facts 4.0 s), the comparator 3.7 s, `recorded_symbols` (parsing the 21.9 MB `progress.json`) 1.0 s
  per solve, the frontier key's `code_digest()` (reads and hashes 83 engine files per function) 5.2 s on the 9p mount
  (tens of ms on ext4, where P7 runs from a snapshot).
* The 809 solved-or-tried functions use 375 distinct unit/class pairs: class facts are recomputed for 434 of them within
  one campaign, and for all 809 in the next one although no header changed.
* Projected from the profile and the records: compiles (candidates 841, class facts about 1,600) and comparator runs are
  about 30% of campaign worker time, all of it repeatable across campaigns whose headers and candidates do not change.

What this means for the order of the work: a dependency digest that contains the engine's whole code (C6 as written)
changes at every merge, so incremental campaigns (item 2) skip nothing at a checkpoint unless the code part is refined
per function; the reach closure contains the inference and synthesis code that P8 and P9 change. Content-addressed
caches (item 3) pay at every campaign whose candidates and headers repeat, which is most functions at most checkpoints.
Item 3 comes first in this round; item 2 needs the per-function code dependency, designed in D12-005.

### D12-003 · 2026-11-27 · Audit of the dependency digest (C6): inputs it omits

An omitted input is a correctness bug (C6), not a cache miss. Read in the code at `11ee7ba`:

| Where | Omits | Consequence |
|---|---|---|
| `manifest.frontier_key` | the include closure of the unit header (only the header's own text is keyed); `progress.json` and `reports/<build>/symbol-map.json` (the resolver of `distance` and the placeholders read them); the comparator's code (`tools/`); the toolchain beyond the recipe's `cl.exe` digest | a saved frontier is resumed with compile and verdict answers from different inputs: a candidate judged with an old symbol map keeps its old distance and may never be verified |
| `manifest.inputs` | the engine's code (only `ENGINE_VERSION`); the knowledge facts the function read (namespaces and values); the toolchain beyond `cl.exe` (the compiler's DLLs `c1xx`/`c2`, the toolset and SDK headers, the wrapper scripts); a dirty upstream worktree (only `HEAD` is keyed) | two runs with different engines or stores have one manifest |
| `campaign.engine_code` (the journal) | every input but the engine's code: image, upstream revision, store namespaces, toolchain, `--next`, `--solve-set` | a campaign resumed after the store or the worktree changed keeps records made from the old inputs |

These are P7's modules. The caches of D12-004 do not use them as keys: each cache key is built from the full inputs of
the one computation it stands for. Fixes to the three are proposed to P7 (a separate commit, P7 reviews).

### D12-004 · 2026-11-27 · A content-addressed compile cache at the compiler's process boundary (in progress)

`adapters/x64_msvc/ccache.py`, consulted by `cl.Toolchain.run`, so every compile of the engine (solve's candidates, class
facts, batches) goes through one place. Off unless `RECON_COMPILE_CACHE` names a directory (inherited by workers). The key
is a digest of: the toolchain (every file of the toolset's binary and header directories, the SDK header directories the
wrappers name, the wrapper scripts, `wine --version`; 7.5 s once per process), the environment `run` gives the compiler,
the whole command line, the working directory, the source's text, and for every `#include` of the source and of every
project file reached every place the compiler may look (all directories of the closure, a superset of any one include
path's), existing ones by content and missing ones as absent. Never cached: a flag outside an allow-list, `/I`, more than
one source, an include through a macro, `__has_include`, `#import`, `include_alias`, `__DATE__`/`__TIME__`/`__TIMESTAMP__`.
The value is the exit code, the output and, only when the compile succeeded, the object; a torn entry is no entry.

For a hit to happen across functions and runs, solve's temporary unit header, source and work directory are now named by
data directory and unit instead of by a clock (so the object's `S_OBJNAME` and the diagnostics are a function of the
inputs), and every use writes, compiles and reads them under the unit's file lock. An object the cache answered is
compiled again before the comparator judges it (C5: the exact unit is compiled and compared last); a fresh object that
differs but for the time stamp raises `CacheMismatch`. That `solve.py` change is a separate commit for P9's review.

Equivalence (section 6) is being run: a fixed stratified sample of 100 plus the 98 functions D-060 matched, main's engine
without the cache against this branch with a cold and a warm cache, sequential, parallel, and killed and resumed
(`scripts/p12_equivalence.py`, which captures source digests and every comparator verdict in the worker).

The first two attempts are void, and the fault was the harness's. The baseline (main's engine, no cache) took
2,035 s and matched 84 of 198. Every run after it, main's engine included, had all 98 functions solve tried blocked
`UNIT_HEADER_DOES_NOT_COMPILE`: 0 matches, 0 verdicts, the store digest unchanged. The output of the failed compiles,
which the harness now keeps, showed the cause: `C1083 Cannot open compiler generated file`. Those runs were given a
relative data directory, and class facts compiles in the upstream worktree with `/Fo` under the data directory, so the
object path named a directory there that does not exist. The baseline had been given an absolute path. The harness now
resolves its paths.

Finding for P7/P9 (latent; P7's runs pass absolute paths): the engine does not resolve the data directory before it
hands it to a compiler running elsewhere. A failure to write the object (C1083), which is a fault of the machine or of
the call, is recorded as the header's blocker `UNIT_HEADER_DOES_NOT_COMPILE`; it should be `INFRA`.
